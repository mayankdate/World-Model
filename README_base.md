# Horizons — Base Specification

*What this project is, what data it uses, how that data is processed, and how the result is used. This document describes the **intended design**, independent of the current state of the code. It is the reference to build against.*

---

## 1. Purpose

A self-contained HTML dashboard, generated by an R pipeline, that visualises global development indicators on a fixed 1990–2100 time axis and runs a small integrated assessment model (IAM) coupling climate, economy, and demography.

**Framing principle: bound futures, don't predict them.**

- Keep horizon-layers dimensionally distinct (observed / demographic projection / climate projection / structural projection).
- Let reach and band-width encode confidence.
- Never let a wide-band guess masquerade as fact.
- Never collapse signals into a single composite index.

The dashboard is personalised to a user born in **1996**: every chart carries faint age-milestone lines (age 30 at 2026, 40, 50 … 100), so trends read against a human lifespan rather than an abstract century.

## 2. Hard constraints

These are non-negotiable design parameters. Any proposed change that violates one needs an explicit decision to relax it.

1. **Zero runtime dependencies.** The output is one `dashboard.html` file (~3 MB) that opens offline in any browser. No D3, no CDN, no web fonts, no server. All charting is hand-rolled SVG in vanilla JS.
2. **R owns the model; JS only evaluates it.** The coupled model is defined once in R as a declarative spec (parameters + named functional forms), serialised to JSON, and injected. The JS contains a small evaluator library of named forms and no model logic. Changing a coefficient, a range, a citation, or adding a whole edge is an R-side data change; sliders and citation text regenerate automatically.
3. **One indicator registry.** `config/indicators.csv` is the single source of truth for what gets fetched. Everything derivable from `source` is derived, not stored redundantly.
4. **No file-navigation friction.** The template lives in `Scripts/` beside the code that uses it. No scattered config objects.
5. **Model integrity rules.** Every coupling edge cites a published empirical estimate; sliders span the literature's *disputed* range, not arbitrary tuning; structural modelling choices are flagged `kind="structural"` and marked as such in the UI; edges with no defensible estimate are **absent**, not guessed.

## 3. Data sources

| Source | Rows | Role | Reach |
|---|---|---|---|
| World Bank API | 28 | Observed history | Structurally projected (short cap) |
| OWID (incl. V-Dem) | 15 | Observed history | Structurally projected (short cap) |
| UN WPP 2024 | 4 | Demographic projections with the UN's own prediction intervals | 2100 |
| CCKP (CMIP6) | 3 | Climate projections, scenario-aware (SSP1-2.6 / 2-4.5 / 5-8.5) | 2100 |

~30 countries embedded (all G20 + pivotal states). GDELT was evaluated and **dropped**: it measured media coverage, not reality.

**Access notes.** World Bank, OWID, and CCKP are open. UN WPP data endpoints require a bearer token, read from `WPP_API_TOKEN` or a gitignored `config/.wpp_token` — never hardcoded. The WPP `locations/all` endpoint returns HTTP 500, so locations are fetched per-country; the location list mixes real countries with UN analytical aggregates that must be filtered by name pattern and by the rule that any ISO3 mapping to more than one location id is not a sovereign country.

## 4. Schemas

### Registry (`config/indicators.csv`) — 8 columns

`indicator, module, source, source_id, unit, direction, description, weight`

`source` ∈ {`worldbank`, `owid`, `unwpp`, `cckp`}. `direction` ∈ {`higher_is_better`, `lower_is_better`}. `module` groups indicators into families (climate, demographics, economy, health, labor, rights, stability, technology). `weight` is optional and unused unless a composite index is ever built (currently: never).

Derived from `source` at load time, so there is exactly one source of truth per fact:

- `worldbank` / `owid` → observed history, projected structurally, short horizon cap
- `unwpp` → demographic projection to 2100, UN's own bands
- `cckp` → climate projection to 2100, scenario-aware

**Invariant:** any lookup table keyed by indicator name (e.g. the WPP numeric portal-id map) must use the exact registry `indicator` string. A mismatch fails silently as "no data".

### Canonical panel — 8 columns

`country_iso3, year, indicator, series_type, scenario, value, lower, upper`

`series_type` is the contract that keeps layers honest — it maps to line style and how far a line is allowed to reach:

| `series_type` | Meaning of the band |
|---|---|
| `observed` | none (`lower = upper = value`) |
| `projection_demographic` | UN 80/95% prediction interval (externally authored) |
| `projection_climate` | CMIP6 inter-model spread p10–p90 (**not** a forecast PI) |
| `projection_structural` | interval from our own fit (calibrate!) |
| `nowcast` | present-moment estimate, no forward reach (unused since GDELT was dropped) |

Bands mean different things per layer and must never be compared across layers as if they were the same object. Layers are kept as **distinct rows**, never blended.

## 5. Pipeline

```
Scripts/
  00_helpers.R              paths, schema contract, HTTP retry, registry loader, token read
  01_fetch_data.R           four source families -> data/raw/ cache (one CSV per thing)
  02_process_project.R      harmonise -> panel.csv; project -> panel_full.csv;
                            build_coupling_spec() -> coupling_spec.json; append ledger
  03_Dash.R                 inject META + DATA + COUPLING into template -> dashboard.html
  dashboard_template.html   the app (HTML + CSS + vanilla JS)
config/
  indicators.csv            the registry
data/raw/                   raw cache (refresh flags in 01 control re-download)
data/output/                panel.csv, projections.csv, panel_full.csv,
                            coupling_spec.json, dashboard.html
data/calibration/           ledger.csv (append-only forecast track record)
```

**Run order matters.** `02` writes *both* `panel_full.csv` and `coupling_spec.json`; `03` consumes both. Running `03` alone after changing the model produces a dashboard with stale coupling. Treat `02 → 03` as one step.

**Stage 1 — fetch.** Everything that touches the outside world, in one place. Four independent sections sharing one skeleton (cache-check → retry → parse → write one CSV per thing). A dead endpoint logs and moves on; it never aborts the run. Refresh flags force re-download.

**Stage 2 — harmonise.** Each source's idiosyncratic shape is normalised into the canonical schema, and this is where the observed/projection split is drawn, so layers are distinct rows from the first table onward. WPP needs a sex filter ("Both sexes" only) and an age-total filter before dedup, or values silently mix.

**Stage 3 — project.** Structural indicators get a forward projection from recent observed history, with an uncertainty band that widens with horizon and a hard horizon cap. Projections must respect each indicator's natural bounds (a share can't exceed 100, an index can't leave [0,1], a rate can't go negative) — including the *band*, not just the central line. Every forecast point is appended to the calibration ledger with its issue date, horizon, and claimed interval, plus an empty `realized` slot.

**Stage 4 — build.** Filter to the embedded country set, clip observed history to 1990+, thin values to 5 significant figures, structure as `indicator → country → [points]` with one-letter type codes, and inject `META`, `DATA`, and `COUPLING` at the template's `__DATA__` token.

## 6. The coupled model (IAM)

The substantive contribution: most projections treat each indicator independently; this one couples them and integrates forward, so a climate shock propagates into income, longevity, and population.

**Spec structure.** `params` (each with default, disputed min/max, step, citation) and `edges` (each with `from`, `to`, a named `form`, which params it `uses`, `kind` ∈ {empirical, structural}, description, citation, and a `contested` note). Plus `notes` on the driver, uncertainty semantics, and provenance.

**Evaluator forms** implemented in JS, one per named form in the spec. Adding an edge that uses an existing form requires no JS at all; a genuinely new functional form requires adding one pure function to the library.

**Baseline edges** (temp → GDP, GDP → life expectancy, temp → life expectancy, GDP → population, temp → population) with published sources. Governance couplings (polarisation → life expectancy, etc.) are deliberately **omitted** — no defensible estimate.

**Driver discipline.** The chain is driven by `mean_temperature` (CMIP6 `tas`), never `max_temperature`, because the BHM optimum is defined on annual-mean temperature. `max_temperature` is a national annual mean of daily maxima — it understates lived extremes (a 45 °C Mumbai afternoon is invisible in it) and is a **display layer only**.

**Validation anchor.** The temp→GDP channel must reproduce BHM's published country pattern: poorest/hottest countries losing roughly 90% of income by 2100, richest/coldest flat-to-positive, averaging to their headline global figure. This is the regression test that has already caught two magnitude bugs.

## 7. How it's used — the four tabs

**World view** — six composite interpretive panels: population & aging (line thickness = dependency ratio, node labels = median age); thermal future (mean temp + max envelope + heat-index stripe); Gini/unemployment; health line-bubble (life expectancy with physician-count bubbles); democracy thick-vs-thin (liberal vs electoral, red gap-shading where electoral exceeds liberal — the illiberal signal); civic fabric (selectable V-Dem index). Includes a **difference-vs-reference toggle**: pick a reference country and every panel re-renders as gaps from it.

**Coupled model** — the IAM. Sliders for every spec parameter, one plot per coupled quantity, naive (uncoupled) vs coupled lines, uncertainty fan, and a citation panel generated from the spec.

**Plot** — indicator families. Pick a module; every indicator in it renders for the selected countries **with all uncertainty bands shown** — the honest, unembellished view that World view suppresses for legibility.

**Scorecard** — one country, all indicators. Scrolling tiles grouped by domain on the left (latest value + direction-aware trend), pinned plot on the right.

**Shared chrome:** country chips, climate-scenario selector, fixed 1990–2100 axis, `NOW` line at the true system year, per-panel data-edge line where observed ends and projection begins, age-milestone lines.

## 8. Verification practice

No R runtime in the dev sandbox, so:

- **R** is validated by comment- and string-aware bracket-balance checks plus Python harnesses that mirror the statistical formulas and test them on synthetic data with known truth. The user runs R locally and pastes output.
- **JS** is validated by executing the template's script in Node against synthetic archetype countries injected exactly as `03_Dash.R` would, asserting model behaviour; and by rendering in headless Chromium (Playwright) with console-error capture, DOM-node counting, and synthetic hover/click events.

This practice has caught: a page-killing million-pixel stroke (dependency ratio holding population counts instead of a ratio); a hover system creating ~2,400 event-bearing circles that froze the browser (replaced with one shared listener per panel using 2D pixel-distance nearest-point); and both IAM magnitude bugs.

**Rendering in a real browser is not optional before shipping.** Node harnesses verify model logic, not paint.

## 9. Standing limitations of the design

These are properties of the approach, not bugs:

1. **Climate is projection-only.** CCKP/CMIP6 provides no observed history, so the climate panel is entirely modelled — correctly labelled, but with no observational anchor.
2. **`max_temperature` understates lived extremes.** Display layer only; never drives the model.
3. **Structural projection of expert-coded V-Dem indices is epistemically dubious** regardless of how well-behaved the arithmetic is.
4. **Per-country coupling is less standard than the literature's global/regional IAMs** (DICE, FUND), and return edges are less cleanly identified at country level.
5. **Coefficients are encoded from published headline values** retrieved via literature search, not from supplementary tables. Verify against source before citing specific numbers.
